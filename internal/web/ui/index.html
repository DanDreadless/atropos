User guide

Atropos user guide

Atropos takes the artefacts of an investigation, keeps an untouched copy of each, reads what it can from them, and puts every dated thing it finds on one timeline in UTC. This guide goes through the screens in the order you are likely to use them.

Getting started

A case is a folder. Start Atropos with atropos serve --case and the folder's path, and open the address it prints, including the part after ?token=. The token changes each time the server starts, so an old bookmark will ask you to use the new address.

  1. Add evidence. Drag files or whole folders onto the page, or press Add evidence. Add everything from one computer together, and include its SYSTEM registry hive if you have it: that is where Atropos learns the computer's name and time zone.
  2. Watch it arrive. Progress shows beside the tabs. The timeline fills as each file is read; you do not have to wait for the last one.
  3. Look. The chart across the top of the timeline shows where the activity is. Drag across a busy stretch to zoom in on it.
  4. Narrow it. Type in the search box, or click the chips under it: Evidence of answers questions such as "what ran?", and Source picks one kind of artefact.
  5. Keep what matters. Click an event to open it, tag it, or tick several and put them in a group of their own.
  6. Write it up. Fill in Details, run Verify integrity, and take a Case report.

Adding evidence

Anything can be added. Atropos works out what a file is from its contents, never from its name, so a renamed file is still recognised. What it has a reader for goes on the timeline. Everything else is still hashed, stored, and has its text indexed so that a search can find it.

For each file, in this order:

  1. It is copied into the case's vault while SHA-256, SHA-1 and MD5 are worked out. The original is only ever read.
  2. The arrival is written to the audit log with the hashes, who added it and when.
  3. It is identified, and the reason is recorded ("signature regf at offset 0").
  4. It is read by a separate worker process, so that a damaged or hostile file cannot take the rest of the case down with it.

Archives (zip, tar, gzip) are unpacked, and each file inside becomes evidence in its own right, listed under the archive. Disk and disc images are not unpacked: see Disk and disc images below. A file whose contents are already in the case is recorded as a duplicate and not read a second time.

Submissions. Files added in one go form a submission. The host name and time zone found in a SYSTEM hive apply to the rest of the same submission, which is why a computer's artefacts belong together and two computers' artefacts belong in two submissions.

Registry hives and their logs. A hive copied from a running computer is often missing its last changes, which Windows keeps for a while in the hive's transaction logs (NTUSER.DAT.LOG1, .LOG2 and so on). Add the logs with the hive. Atropos matches them to their hive by what is inside them, applies them the way Windows would on loading the hive, and says in the hive's notes which logs and entries it used. If a hive needs its logs and they are not in the case, its status is partial and the notes say so; add the logs later and the hive is read again by itself.

Files dropped onto the page arrive without their alternate data streams, because a browser cannot see them. To keep the Zone.Identifier of downloaded files (it records where each came from), add the folder with atropos ingest on the command line instead.

Reading the timeline

Each row is one moment that an artefact recorded. The columns, left to right:

Time (UTC)Always UTC, to the precision the artefact holds.
TZA coloured dot for how the time zone was established. Hover over it. An orange row means the zone was assumed: treat that time with care (see Time zones).
MACBFor file times only: Modified, Accessed, Changed (the file's record, not its content) and Born. Dots mean the time is not a file time.
Evidence ofWhat the event tells you: a program ran, a file was opened, an account was used, something was set to start automatically, and so on.
MeaningWhat this particular time is. "program-last-run (prefetch)" and "file-modified (shimcache)" are different claims even when they name the same file.
SourceThe kind of artefact: event log, registry, file table, browser and so on.
Host, UserWhere the artefact says them. Often empty.
ItemThe evidence file the event was read from. Hover for its full path; for a file taken out of an image, the path starts with the image.
MessageThe event in a sentence, with any tags and groups in front.

The chart. Each bar is a slice of time and its height is the number of events in it, for the current search. Drag across bars to zoom to that span. Zoom out steps back and Whole timeline returns to everything. The line above the chart says how many events match and the period they cover.

Order. The button beside the search box switches between oldest first and newest first.

Opening an event. Click a row. The panel on the right shows the time to the nanosecond and as it was found in the source, how the zone was arrived at, every field the reader extracted, where in the file the record sits, and which evidence item and parse run it belongs to. From there you can jump to that item, show only its events, or show everything from the image it came out of. A change-journal record names its folder only by a number in the file table; when the file table from the same volume is in the case, the panel shows that folder's path too, as the file table records it now.

The address bar always holds the current view, search, zoom and open event. Copy it into your notes and it will bring you back to exactly that place while the same server is running.

Searching

Words are matched from their start and all of them must be present, so powersh enc finds events mentioning both "powershell" and "encodedcommand". Everything else is a filter of the form name:value. Put a minus sign in front of a word or a filter to exclude it.

"exact phrase"The whole word or phrase, not just its beginning.
-svchostLeave out events that mention it.
category:executionOne "Evidence of" group. The chips do the same.
source:evtxOne kind of artefact.
type:"program-last-run (bam)"One exact meaning. Use quotes when it has spaces.
host:PC1   user:aliceAs the artefact recorded them.
macb:m   macb:mbFile times that are a modification; or both modified and born.
tz:assumedEvents whose zone had to be assumed.
tag:anomaly   group:MalwareEvents you, or an analysis, have marked.
evidence:12Events read from item 12 alone.
from:12Item 12 and everything that came out of it: all files taken from an image, all members of an archive.
file:ntuserEvents from any item whose name or path contains the text. file:"Users/alice" works on paths inside an image.
submission:2Everything added together in the second submission.
id:41,57Those events exactly. Analysis findings use this to point at the timeline.

Filters combine: from:3 category:execution -source:registry powershell is "programs run, according to anything but the registry, among what came out of image 3, mentioning PowerShell".

Text inside files. When your search has plain words in it, files whose own text contains them are listed above the table, even if they put nothing on the timeline. A script, a note, or a file Atropos has no reader for is found this way.

Finding what came from where

A case soon holds hundreds of items, many of them copied out of one image. Four things keep them apart:

  • The From list, beside the search box. It lists every image and archive that things were taken out of, with the number of events each accounts for, and every submission. Pick one and the timeline shows only that, and the counts on the Evidence of, Source and Time zone from chips change to count only that too. Pick all evidence to go back. Viewing a group does the same to the counts.
  • The Item column names the file each event was read from.
  • On the Evidence tab, open an image or archive and press Show all events from it and what came out of it. Open any single item and press Show its events.
  • On the Files tab, Show its events does the same for the image you are browsing.

These all write a from:, evidence: or submission: filter into the search box, so you can add words and other filters after it.

Disk and disc images

An image can hold a million files, nearly all of them irrelevant, so it is not unpacked when it arrives. Open the Files tab, choose the image, and browse it like a folder.

  • Add standard Windows artefacts walks the image for the files an investigation usually wants (registry hives, event logs, prefetch, the file table and change journal, shortcuts and jump lists, browser profiles, scheduled tasks, Defender's records, the WMI repository and more) and copies them out.
  • Or tick files and folders yourself and press Add selected to timeline.

Whatever is copied out is hashed, stored and read like any other evidence, and is listed under the image on the Evidence tab. Files with an alternate data stream show it as a separate line; a file's Zone.Identifier is taken along with it automatically.

What can be opened: ISO 9660 discs, NTFS volumes, raw disks partitioned with MBR or GPT that hold NTFS, and any of those inside an EnCase or FTK Imager image (.E01), a Hyper-V or Virtual PC disk (.vhd, .vhdx, fixed, dynamic or differencing) or a single-file VMware disk (.vmdk, sparse or stream-optimised).

Differencing disks hold only what changed since their parent disk. Add the parent too: Atropos finds it among the case's images by the identifier the two share, whatever it is called. Without it, the image's notes say which parent is missing.

E01 images. Add every segment file (.E01, .E02 and so on). They are matched by an identifier inside them, so their names do not matter and you can add them in any order. When the set is complete Atropos reads the whole image, checks every block against its own checksum, and compares the hash of the contents with the hash the imaging tool stored. The first segment's notes then say verified, or NOT VERIFIED with both hashes. If a segment is missing, the notes say which, and the check runs by itself when it arrives. The acquisition details recorded in the image (case number, examiner, notes) are kept as facts.

Volume shadow copies are listed, with the time each was made, in the image's description. Their contents are not read; mount the image with a tool that can and add the files you want.

The Evidence tab

One row for every item in the case. Click a row for its hashes, where it came from, how it was identified, which reader handled it, and that reader's notes.

parsedRead by the reader for its kind, without complaint.
partialRead, but something was skipped or could not be decoded. The notes say what. The events that did come out are sound.
genericNo reader for this kind, or the reader found nothing it recognised. The file's text is indexed, and a program's build time is taken, but nothing else.
unpackedAn archive; look at the items under it.
duplicateThe same contents as an earlier item. Stored once, read once.
queued, processingWaiting its turn, or being read now.
interruptedAtropos was stopped while reading it. Press Parse again.

Sorting and filtering. The list starts in the order things were added, with each file under the image or archive it came out of. The box at the top filters by name, path, type, status or hash. The list beside it re-orders by number of events, name, type, status or size, and With events only hides everything that put nothing on the timeline.

Parse again reads an item afresh as a new run. The earlier run and its events are kept in the case and remain verifiable; the timeline shows the newest. Tags, comments and group membership belong to the earlier run's events and do not move across, so re-parse before you annotate, not after.

After an upgrade. Readers improve between versions. An item read by an earlier version than the one now running is marked older, and a button appears at the top: Bring N items up to date. It parses all of them again in one step.

Tags, comments and groups

Your notes sit in a layer of their own. They never alter an event, and every one is recorded in the audit log under your name.

  • Tag or comment: open an event, type in the box under Examiner notes, and press Add tag or Add comment. Enter adds a single word as a tag and anything longer as a comment. Tags show in front of the event's message and can be searched with tag:.
  • Withdraw a note from the same panel. It is struck through, not erased: the record shows that it was made and that it was withdrawn.
  • Groups are timelines you build from picked events: one for the intrusion, one for the exfiltration, one for a single user. Press + New group, then tick events (shift-click ticks a run of them) and choose the group from Add selected to group. With nothing ticked, the same list adds every event matching the current search. Click a group's chip to see only its events; Everything returns to the whole case.
  • A group can be exported or reported on by itself. Archiving a group hides it; nothing is deleted.

Analysis

Two sets of checks that no single artefact can make. Neither adds events. Each run is recorded in the audit log, and every finding opens the events behind it.

Things out of place looks at every event for what does not belong where it was found: a Windows program name in the wrong folder, a name one character away from a real one, programs run from temporary or public folders, things set to start automatically from such places, cleared logs, antivirus detections, commands of the kind intruders use, downloads the browser judged dangerous, browser extensions loaded from a folder, and WMI subscriptions that run a command. Each kind says why it matters and, just as important, what innocent thing also looks like this.

Contradictions about file times compares what the file table says about a file with what other artefacts recorded independently (ShimCache, Amcache, the change journal, the transaction log, old directory entries). A file whose times were set backwards disagrees with at least one of them. This needs a file table in the case.

A finding is a place to look, not a conclusion. Tag these as anomalies gives every event listed the tag anomaly, in your name, so that they stand out on the timeline and can be searched.

Case and host details

A report needs facts no artefact holds: the case reference, who asked for the examination, and for each computer its make, model, serial number, who collected it and how, and what its clock read against a reference when it was seized. Enter them on the Details tab. Where Atropos found a value in the evidence (the host name, the time zone, the Windows version) it is shown beside the field for comparison. Changes are kept as a history; an earlier value is never overwritten.

Reports and exports

Case report (top right) first verifies the case, then writes one document: what was examined, with hashes; how each item was read and by which version; the details you entered; your groups and notes; and the result of the verification. HTML is for reading and printing, JSON for other tools.

Export (beside the search box) writes the events that match the current search, zoom and group:

CSVFor a spreadsheet. Values that a spreadsheet would treat as a formula are made safe.
JSON linesOne event to a line with every field. The fullest form.
Timesketch JSONLReady to upload to Timesketch.
BodyfileFile times only, for mactime and tools that read its format.

Every export and report is recorded in the audit log with what was asked for.

Integrity and the audit log

Nothing in a case is ever changed or deleted. Evidence is stored once under its hash. Events belong to the parse run that made them, and each run is sealed with a digest of its events. Corrections are new entries. The Audit log tab lists everything that has happened, each entry carrying the hash of the one before, so that an entry cannot be altered or removed from the middle without it showing.

Verify integrity re-hashes every stored file, recomputes every run's digest from the events as they are now, compares the runs with what the audit log recorded when each was sealed, and walks the audit chain. It ends with the hash of the newest audit entry. Write that down somewhere outside the case: it is what later proves that nothing was removed from the end of the log.

Time zones

Everything on the timeline is UTC. Many artefacts store UTC already. Others store the computer's local time with no zone, and those have to be converted. The TZ dot on each row says how:

native-utcThe format stores UTC. Nothing to decide.
explicit-offsetThe value carried its own offset.
host-registryLocal time, converted with the zone read from the computer's own SYSTEM hive in the same submission. This is why the hive should be added with the rest.
examiner-setLocal time, converted with a zone you stated when starting Atropos (--local-zone Europe/London). Your statement is in the audit log.
assumedNo zone could be established, so the time was taken as UTC. It may be wrong by the computer's offset. These rows are orange; tz:assumed finds them all.

A local time that falls in the hour repeated or skipped when the clocks change cannot be converted with certainty. Such an event carries a caveat, shown when you open it.

Command line

Everything the page does to a case can also be done without it. One Atropos process works on a case at a time.

atropos serve --case DIRThis interface. It listens only on this computer.
atropos ingest --case DIR PATH…Add files or folders. On Windows this keeps alternate data streams, which the page cannot.
atropos verify --case DIRThe integrity check.
atropos export --case DIR --format csv --query "…" -o FILEExport a search. Formats: csv, jsonl, timesketch, bodyfile. --group NAME for one group.
atropos report --case DIR --format html -o FILEThe case report.
atropos analyse --case DIRBoth sets of checks. --check anomalies or timestamps for one; --tag to tag what the anomaly checks find.

Useful with any of them: --examiner NAME (recorded in the audit log; your login name otherwise) and --local-zone ZONE. Run atropos with no arguments for the full list.

Limits worth knowing

  • A finding, a tag, or an event is evidence of what the artefact recorded, and no more. "File modified (ShimCache)" is the file's modification time as Windows cached it, not the time it ran.
  • A browser database copied from a running browser may have its newest entries in a separate -wal file, which is not applied. The item's notes say so.
  • Synced browser history is marked as such: a visit made on another device signed in to the same account is not evidence that this computer was used.
  • Cookie values and saved passwords are never read. Atropos records that a cookie or a saved login exists, for which site, and when.
  • Records found by searching (WMI subscriptions, entries in unused directory space) may be old or deleted versions. Their notes say how they were found.
  • A deleted registry key is shown at the time it was last written, which is before it was deleted, not the moment of deletion. When its parent key is also gone, its path starts with …\. Search type:"registry-key-deleted (last written)" to see them all.
  • Memory images are out of scope. Use Volatility, and add what it produces as a log if you want it on the timeline.
  • Not opened yet: VHDX and VMDK images, FAT and exFAT volumes, the contents of shadow copies. The README lists what each reader covers and docs/COMPARISON.md how its output compares with other tools.
  • The timeline loads rows as you scroll. In a case of millions of events, zoom in on the chart to move around; do not try to scroll the whole of it.
