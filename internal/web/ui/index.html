Atropos user guide

Atropos takes the artefacts of an investigation, keeps an untouched copy of each, reads what it can from them, and puts every dated thing it finds on one timeline in UTC. This guide goes through the screens in the order you are likely to use them.

Getting started

A case is a folder. Start Atropos with atropos serve --case and the folder's path, and open the address it prints, including the part after ?token=. The token changes each time the server starts, so an old bookmark will ask you to use the new address.

  1. Describe the hosts. On the Details tab, add each computer the case is about: its name, and its time zone as a zone name such as Europe/London.
  2. Add evidence. Drag files or whole folders onto the page, or press Add evidence, and say which host they come from (or that they come from none, and where from). Add everything from one computer together, and include its SYSTEM registry hive if you have it: Atropos reads the computer's name and time zone from it and tells you if they disagree with what you stated.
  3. Watch it arrive. Progress shows beside the tabs. The timeline fills as each file is read; you do not have to wait for the last one.
  4. Look. The chart across the top of the timeline shows where the activity is. Drag across a busy stretch to zoom in on it.
  5. Narrow it. Type in the search box, or click the chips under it: Evidence of answers questions such as "what ran?", and Source, on the row below, picks one kind of artefact. Time zone from, under the chart, picks events by how their time zone was established. The chips always count what the search finds: type a word and they show only the kinds of event and artefact that hold it. Within one row, the counts leave out that row's own choice, so after picking execution you can still see how many account events there are and add them: chips picked in the same row mean either (execution or account), while chips in different rows narrow each other (execution from the registry).
  6. Browsing. The browser source is what this machine's browser recorded; browser-synced is history that sync brought from another device signed in to the same account, which is not evidence that this machine was used. Under Evidence of, browser is pages someone opened and downloads; browser-automatic is what the browser loaded by itself (hops in a redirect chain, frames inside a page, start-up pages). The Meaning column says how each page was reached: url-visited (typed), (link), (form submitted), (reload) and so on. Open a visit for a read-out: the page, how it was reached, the page it came from (with a button that opens that visit, to walk the chain back), the search, the time on the page, and whose profile it was (taken from the folder the history file came from, and marked as inferred). Addresses are shown as text and never opened.
  7. Keep what matters. Click an event to open it, tag it, or tick several and put them in a group of their own.
  8. Write it up. Fill in Details, run Verify integrity, and take a Case report.

Adding evidence

Anything can be added. Atropos works out what a file is from its contents, never from its name, so a renamed file is still recognised. What it has a reader for goes on the timeline. Everything else is still hashed, stored, and has its text indexed so that a search can find it.

Which host. Every submission is assigned before it is sent: to a host described on the Details tab, or as not from a host with a description of where it came from (a packet capture, firewall or cloud logs, a phone export), which is kept with it and shown in the report. Its events carry the host's name, so the timeline can be read across several computers (the Host chips, host:), and the time zone stated for the host is used for times its files record in local time; a zone read from a SYSTEM hive in the same submission takes precedence, being evidence. When a SYSTEM hive names a different computer from the host chosen, the item's notes say so. An event log can hold records from other machines (forwarded events): those keep the computer they name in their computer field. To correct a choice, open any item of the submission on the Evidence tab and press Change host…: the change is recorded, and the submission's items are parsed again under the new host.

For each file, in this order:

  1. It is copied into the case's vault while SHA-256, SHA-1 and MD5 are worked out. The original is only ever read.
  2. The arrival is written to the audit log with the hashes, who added it and when.
  3. It is identified, and the reason is recorded ("signature regf at offset 0").
  4. It is read by a separate worker process, so that a damaged or hostile file cannot take the rest of the case down with it.

Archives (zip, tar, gzip) are unpacked, and each file inside becomes evidence in its own right, listed under the archive. Disk and disc images are not unpacked: see Disk and disc images below. A file whose contents are already in the case is recorded as a duplicate and not read a second time.

Submissions. Files added in one go form a submission. The host name and time zone found in a SYSTEM hive apply to the rest of the same submission, which is why a computer's artefacts belong together and two computers' artefacts belong in two submissions.

Registry hives and their logs. A hive copied from a running computer is often missing its last changes, which Windows keeps for a while in the hive's transaction logs (NTUSER.DAT.LOG1, .LOG2 and so on). Add the logs with the hive. Atropos matches them to their hive by what is inside them, applies them the way Windows would on loading the hive, and says in the hive's notes which logs and entries it used. If a hive needs its logs and they are not in the case, its status is partial and the notes say so; add the logs later and the hive is read again by itself.

Large folders (a browser profile, a user's AppData) are sent in parts, with a progress bar showing files, size, speed and time left; all of it is one submission and is parsed when the last part has arrived. A file the browser cannot read, usually because a program has it open (a web browser holds its own profile open while it runs), is skipped, and you are shown the list; it is also recorded in the audit log. Close the program and add those files again. Do not close the page while an upload is running.

Files dropped onto the page arrive without their alternate data streams, because a browser cannot see them. To keep the Zone.Identifier of downloaded files (it records where each came from), add the folder with atropos ingest on the command line instead.

Files exported by a forensic tool, such as $MFT, $LogFile and $J from FTK Imager, often keep the Hidden and System attributes they had on the volume, and then Explorer and the file picker do not show them. Clear the attributes on your copies (attrib -h -s "C:\exported\*"; the content and its hash are unchanged), type the file's full name into the picker's File name box, or add the folder with atropos ingest, which reads hidden files.

What "Evidence of" means

Every event is put in one group by what it is evidence of, following the "Evidence of…" grouping taught in Windows forensics. The group says what kind of claim the event makes; it does not make the claim stronger than its artefact. Two things hold for all of them:

  • Read the Meaning column with it. The group says what happened; the Meaning says which time this is. "program-last-run (userassist)" and "file-modified (shimcache)" are both execution, but the first is when a person last started the program and the second is the program file's own modified time, which says nothing about when it ran.
  • One artefact is a lead, two independent ones are a finding. Most artefacts below can be explained away on their own (a scan by antivirus, a sync, a restore). Look for the same file or account in a second group or a second source.

execution

A program ran, or Windows recorded it as present to run.

Comes from
Prefetch run times; UserAssist and BAM (last run, per user); ShimCache and Amcache; SRUM application use; process creation and PowerShell in the event log (Security 4688, Sysmon 1, PowerShell 4103/4104, Task Scheduler 100/200/201, service start and stop 7035/7036); Defender's process telemetry; the Run dialog.
How to read it
Prefetch, UserAssist, BAM, 4688 and Sysmon 1 show a run. ShimCache and Amcache do not prove a run on their own on Windows 10 and 11: they record that Windows saw the file (ShimCache's time is the file's modified time; the "executed" flag is only a hint). UserAssist and BAM name a user; prefetch does not. Prefetch can be turned off on servers and SSD systems.

file-opening

A file or folder was opened, saved or browsed to by a person.

Comes from
Shortcut (.lnk) files and jump lists; the registry's recent documents, Open and Save dialog lists and typed paths; shellbags (folders browsed in Explorer); Explorer searches; Notepad and Notepad++ tabs; OneDrive opening an online-only file; Windows Search's record of opened items.
How to read it
Strong evidence of a person's activity, tied to the user whose profile holds it. A shellbag shows a folder was viewed, not that a file in it was opened. Most of these lists keep only the latest time per entry: an earlier opening is not shown. The file need not exist any more, which makes these good evidence of deleted or removable-media files.

file-system

A file or folder's own times on the volume: created, modified, accessed, record changed.

Comes from
The NTFS file table ($MFT: $STANDARD_INFORMATION and $FILE_NAME times), the change journal ($J), the transaction log ($LogFile), old directory entries in index slack, FAT, exFAT and ext volumes, OneDrive's sync database, shadow copy creation, Sysmon file events.
How to read it
The bulk of most timelines. The $STANDARD_INFORMATION times can be changed by any program (timestomping); $FILE_NAME times and the change journal are much harder to alter, which is what Analysis compares. Accessed times are often not updated by Windows. A copied file keeps its modified time but gets a new created time, so "created after modified" usually means a copy. Antivirus scans and backups touch files too.

browser

A person browsed: pages opened, downloads, searches, form entries, saved logins, sessions, extensions.

Comes from
Chromium and Firefox history, downloads, cookies, autofill, logins (never the passwords), address-bar shortcuts, page icons, bookmarks, session files and extensions; Internet Explorer typed URLs; Windows Search's indexed web history.
How to read it
Check the Source: browser is what this machine recorded, browser-synced came from another device signed in to the same account and is not evidence that this machine was used then. The Meaning says how a page was reached; typed and form submitted show intent, link less so. A cookie shows a site was contacted, not that a person looked at it. History can be deleted by the user; cookies, page icons and Windows Search often outlive it.

browser-automatic

A page the browser loaded by itself: a hop in a redirect chain, a frame inside a page, a start-up page.

Comes from
Chromium and Firefox history, from how each visit was made.
How to read it
Shows the browser contacted that address, not that a person chose it. A redirect hop sits just before the page that was shown (open it and follow Came from). Useful for tracking and malicious redirects; leave it out when asking what someone looked at.

account

An account was used or changed: logons and logoffs, failed logons, remote sessions, accounts created, enabled, changed or locked.

Comes from
Security log (4624 logon with its type, 4625 failed, 4634/4647 logoff, 4648 explicit credentials, 4672 admin rights, 4720-4738 account changes, 4740 lock-out, 4768/4769/4771/4776 Kerberos and NTLM, 4778/4779 reconnects); Remote Desktop and WinRM logs; SAM account times; the account keys' last writes.
How to read it
The logon type in a 4624's fields matters: 2 at the keyboard, 3 over the network, 10 Remote Desktop, 5 a service. Many logons are the system itself. A failed logon is an attempt, not access. The Security log rolls over quickly on busy machines, so absence proves little.

network

Network activity: connections, shares, remote desktop out, downloads by BITS, firewall changes, networks joined, data used.

Comes from
Security 5140/5145 (share access) and 5156 (connections allowed); Remote Desktop client logs; BITS transfers; Sysmon network and DNS events; firewall rule changes; SRUM network connections and bytes per application; network history and mapped drives in the registry; web server logs.
How to read it
SRUM's figures are totals over an hour or so, not single connections, and are written when the period ends. The registry's network list shows a network was joined, with first and last connection. Most connections are not logged at all unless Sysmon or connection auditing was set up.

persistence

Something was set up to run again by itself: services, scheduled tasks, Run keys, WMI subscriptions.

Comes from
Service installs (System 7045, Security 4697) and start-type changes; scheduled tasks (Security 4698-4702, Task Scheduler 106/140/141, the task files and TaskCache); autostart registry keys; Winlogon; WMI event subscriptions in the repository and their log events.
How to read it
A registry key's last-write time says the key changed then, not which value changed or that the entry was added then. Plenty of persistence is legitimate (updaters, drivers): look at the path and the program. A WMI subscription is rare outside management software and worth reading in full.

device

External storage and devices: USB drives connected, volumes mounted, devices installed.

Comes from
Partition and device-driver logs (Partition 1006, DriverFrameworks 2003/2100/2102, Kernel-PnP 400/410), Security 6416; the USBSTOR and mount-point keys; MountPoints2 per user.
How to read it
The Partition 1006 event carries the drive's serial number and size; the registry keys give first and last connection where Windows keeps them. MountPoints2 ties a volume to a user. Match volume serial numbers with shortcut files (file-opening) to show files opened from the drive.

registry

A registry key was written, and nothing more specific is known about it.

Comes from
Every key's last-write time in the hives; deleted keys recovered from the hive; Sysmon registry events and Security 4657.
How to read it
The key's last write covers any change to its values, by anyone, including Windows itself. Use it to date a change you have another reason to look at, not as evidence of activity by itself. Keys Atropos understands appear in the more specific groups instead.

security

Security events: malware detected and acted on, protection changed, logs cleared, the clock changed, shutdowns.

Comes from
Defender's operational log, detection history and support log (MPLog); Security 1102 and System 104 (logs cleared), 4616 (time changed), 4719 (audit policy changed); unexpected shutdowns (6008) and shutdowns (1074); Sysmon tampering.
How to read it
A log being cleared or protection being switched off is significant in itself: it is often the attacker's last step. A detection shows the file was there and named what Defender thought it was; check what action was taken and whether it succeeded.

deletion

A file was deleted.

Comes from
The Recycle Bin's records ($I files); the change journal's delete records; freed ext inodes; OneDrive and its SafeDelete database; Security 4660 and Sysmon file deletes.
How to read it
The Recycle Bin shows a person deleted it through Explorer (and the original path); the change journal shows any deletion, by anything, including temporary files, which make up most of it. A deletion record does not mean the content is gone: check the file table and shadow copies.

log

Any other dated entry: log lines and event-log records with no more specific meaning.

Comes from
Event-log records not listed above, text logs, OneDrive's logs, the E01 acquisition record, SRUM energy records, Defender's log lines.
How to read it
Context, not evidence of a kind of activity. Search them by words and read them around the times that matter.

Text inside files. When your search has plain words in it, files whose own text contains them are listed above the table, even if they put nothing on the timeline. A script, a note, or a file Atropos has no reader for is found this way.

Finding what came from where

A case soon holds hundreds of items, many of them copied out of one image. Four things keep them apart:

  • The From list, beside the search box. It lists every image, every archive that things were taken out of, each with the number of events it accounts for, every name in the timeline's Item column (all the NTUSER.DAT hives, the $MFT, each event log), built from what has been parsed, and every submission. Pick one and the timeline shows only that, and the counts on the Evidence of, Source and Time zone from chips change to count only that too. Pick all evidence to go back. Viewing a group does the same to the counts, as does anything typed in the search box.
  • The Item column names the file each event was read from.
  • On the Evidence tab, open an image or archive and press Show all events from it and what came out of it. Open any single item and press Show its events.
  • On the Images tab, Show its events does the same for the image you are browsing.

These all write a from:, evidence:, item: or submission: filter into the search box, so you can add words and other filters after it.

Disk and disc images

An image can hold a million files, nearly all of them irrelevant, so it is not unpacked when it arrives. Open the Images tab, choose the image, and browse it like a folder.

  • Add standard Windows artefacts walks the image for the files an investigation usually wants (registry hives, event logs, prefetch, the file table and change journal, shortcuts and jump lists, browser profiles, scheduled tasks, Defender's records, the WMI repository and more) and copies them out.
  • Or tick files and folders yourself and press Add selected to timeline.

Whatever is copied out is hashed, stored and read like any other evidence, and is listed under the image on the Evidence tab. Files with an alternate data stream show it as a separate line; a file's Zone.Identifier is taken along with it automatically.

What can be opened: ISO 9660 and UDF discs (a disc with both, such as a Windows install disc, is shown through its UDF side, which holds files of any size), NTFS, FAT12, FAT16, FAT32, exFAT and Linux ext2, ext3 and ext4 volumes, raw disks partitioned with MBR or GPT that hold those, and any of them inside an EnCase or FTK Imager image (.E01), a Hyper-V or Virtual PC disk (.vhd, .vhdx, fixed, dynamic or differencing) or a single-file VMware disk (.vmdk, sparse or stream-optimised).

USB sticks, memory cards and other FAT or exFAT volumes go on the timeline as soon as the image is added, without copying anything out: every file and folder, with its created, modified and last-accessed times. Files marked deleted whose entries are still there are included, marked deleted; their times are the file's own, not the time it was deleted. FAT overwrites the first letter of a deleted file's short name; it is shown as _, or worked out from the long name when that survived. The volume's serial number is kept on every event and as a fact, so it can be matched with the drive serial recorded in shortcut files. Search source:fat to see them all, or source:fat deleted.

Linux volumes (ext2, ext3, ext4) also go on the timeline when the image is added: every name, with its modified, accessed, changed and (on ext4) created times, which are UTC to the nanosecond. When a file is deleted its name often survives in the folder's unused space. Atropos recovers those names and, while the file's inode has not been given to another file, shows its times and an inode freed event at the moment it was deleted (search category:deletion source:ext). Deleting sets a file's changed and modified times to that moment too. A recovered name whose inode now belongs to another file gets no times, since they would be the other file's; the notes count them. Symbolic links are listed with their targets and never followed.

Thumbnail caches (thumbcache_256.db and the rest) open on this tab too, as a folder of small pictures that Explorer once showed, often of files long gone. They record no times. Each thumbnail is named by an identifier that the Windows Search index also records against the file's path: search for it and the index tells you where the picture was.

Differencing disks hold only what changed since their parent disk. Add the parent too: Atropos finds it among the case's images by the identifier the two share, whatever it is called. Without it, the image's notes say which parent is missing.

E01 images. Add every segment file (.E01, .E02 and so on). They are matched by an identifier inside them, so their names do not matter and you can add them in any order. When the set is complete Atropos reads the whole image, checks every block against its own checksum, and compares the hash of the contents with the hash the imaging tool stored. The first segment's notes then say verified, or NOT VERIFIED with both hashes. If a segment is missing, the notes say which, and the check runs by itself when it arrives. The acquisition details recorded in the image (case number, examiner, notes) are kept as facts.

Volume shadow copies are earlier states of an NTFS volume that Windows keeps on the volume itself, often days or weeks apart. Each one appears as a folder at the root of the volume, <shadow copy 1>, <shadow copy 2> and so on, oldest first; its note says when it was made. Inside is the whole volume as it was at that moment: browse it and add files from it exactly as from the current volume. A file copied out of a copy says so in its origin (image!/<shadow copy 2>/Windows/System32/config/SYSTEM), so an older hive or event log sits beside the current one and can be compared. Add standard Windows artefacts takes them from the current volume only; go into a copy and choose what you want from it. A copy whose records are damaged says why when you open its folder; the others are unaffected.

The Evidence tab

One row for every item in the case. Click a row for its hashes, where it came from, how it was identified, which reader handled it, and that reader's notes.

Pictures (JPEG, PNG, GIF, WebP and BMP, recognised by their contents, not their names) are shown in their details here and in the side panel of their events; click a picture to see it full size. Thumbnails copied out of a thumbnail cache are pictures too. Other kinds of file are never shown in the browser: an SVG or a web page named photo.jpg is refused, because a browser would run what is inside it.

parsedRead by the reader for its kind, without complaint.
partialRead, but something was skipped or could not be decoded. The notes say what. The events that did come out are sound.
genericNo reader for this kind, or the reader found nothing it recognised. The file's text is indexed, and a program's build time is taken, but nothing else.
unpackedAn archive; look at the items under it.
duplicateThe same contents as an earlier item. Stored once, read once.
queued, processingWaiting its turn, or being read now, including after Parse again. Hover over the label for the status of the last finished run, which is what the row shows again when the new run ends.
interruptedAtropos was stopped while reading it. Press Parse again.

Sorting and filtering. The list starts in the order things were added, with each file under the image or archive it came out of. The box at the top filters by name, path, type, status or hash. The list beside it re-orders by number of events, name, type, status or size, and With events only hides everything that put nothing on the timeline.

Parse again reads an item afresh as a new run. The earlier run and its events are kept in the case and remain verifiable; the timeline shows the newest. Tags, comments and group membership belong to the earlier run's events and do not move across, so re-parse before you annotate, not after.

Exclude from case… takes an item out of the case's view when it does not belong: the wrong machine's image, a file added by mistake. Give a reason; it is kept in the case and the audit log. The item, and everything that came out of it, leaves the timeline, the chips and counts, the From list, text search, exports, the report's timeline and the checks on the Analysis tab. Nothing is deleted: the file stays in the vault, its runs and events stay stored, Verify integrity still checks them, and the report lists the item as excluded with your reason. Include again brings it all back. Atropos never deletes evidence from a case; to hand over a case without something in it, make a new case without it.

After an upgrade. Readers improve between versions. An item read by an earlier version than the one now running is marked older, and a button appears at the top: Bring N items up to date. It parses all of them again in one step.

Tags, comments and groups

Your notes sit in a layer of their own. They never alter an event, and every one is recorded in the audit log under your name.

  • Tag or comment: open an event, type in the box under Examiner notes, and press Add tag or Add comment. Enter adds a single word as a tag and anything longer as a comment. Tags show in front of the event's message and can be searched with tag:.
  • Withdraw a note from the same panel. It is struck through, not erased: the record shows that it was made and that it was withdrawn.
  • Groups are timelines you build from picked events: one for the intrusion, one for the exfiltration, one for a single user. Press + New group, then tick events (shift-click ticks a run of them) and choose the group from Add selected to group. With nothing ticked, the same list adds every event matching the current search. Click a group's chip to see only its events; Everything returns to the whole case.
  • A group can be exported or reported on by itself. Archiving a group hides it; nothing is deleted.

Analysis

Two sets of checks that no single artefact can make. Neither adds events. Each run is recorded in the audit log, and every finding opens the events behind it.

Things out of place looks at every event for what does not belong where it was found: a Windows program name in the wrong folder, a name one character away from a real one, programs run from temporary or public folders, things set to start automatically from such places, cleared logs, antivirus detections, commands of the kind intruders use, downloads the browser judged dangerous, browser extensions loaded from a folder, and WMI subscriptions that run a command. Each kind says why it matters and, just as important, what innocent thing also looks like this.

Contradictions about file times compares what the file table says about a file with what other artefacts recorded independently (ShimCache, Amcache, the change journal, the transaction log, old directory entries). A file whose times were set backwards disagrees with at least one of them. This needs a file table in the case.

A finding is a place to look, not a conclusion. Tag these as anomalies gives every event listed the tag anomaly, in your name, so that they stand out on the timeline and can be searched.

Connections between hosts

The Connections tab shows how the hosts of the case connected to each other, by putting together what each one recorded of the same connection. It reads three kinds: Remote Desktop, file shares, and programs started remotely (PsExec and tools like it, services and scheduled tasks created over the network, PowerShell remoting and other remote management over WinRM, WMI, and DCOM). USB devices and files by hash are to follow. The buttons above the drawing show one kind at a time.

What it reads for Remote Desktop. On the computer connecting: its Remote Desktop client log (Microsoft-Windows-TerminalServices-RDPClient/Operational, events 1024 and 1102, which name the computer as it was typed and its address) and Security 4648 to TERMSRV/… (credentials given for the connection). On the computer connected to: Security 4624 with logon type 10 or 12, and 4778; RemoteConnectionManager 1149; LocalSessionManager 21, 22 and 25; RdpCoreTS 131.

For file shares and programs started remotely. On the computer connecting: commands that name \\computer (for example net use, a copy, PsExec, PAExec, RemCom or sc), from Security 4688 when process auditing records command lines, or from Sysmon event 1; and Security 4648 to cifs/…. For remote management and WMI, also commands that name the computer their own way (wmic /node:, winrs -r:, schtasks /s, and PowerShell's Invoke-Command, Enter-PSSession, New-PSSession and WMI and CIM commands with -ComputerName), the WinRM log's event 6 (a session being created to a computer), and Security 4648 to RPCSS/… or WSMAN/…, or to HTTP/… from PowerShell. On the computer connected to: Security 5140 (a share connected to) and 5145 (a file or pipe on it), which Windows logs only when file share auditing is on; System 7045 and Security 4697 (a service installed); Sysmon 1 for PSEXESVC.exe starting; Security 4698 and 4702 (a scheduled task made or changed); the WinRM log's event 91 (a remote shell created); and, from Security 4688 or Sysmon 1, the PowerShell remoting and winrs hosts (wsmprovhost.exe, winrshost.exe) starting and the programs they start, and programs started by WMI (WmiPrvSE.exe). It counts as started remotely when the service manager's or Task Scheduler's pipe (svcctl, atsvc) is opened over the network, when pipes are named as PsExec names them, when a program is written to ADMIN$, or when a service is installed, a task made, a remote shell created, or a program started by those hosts or by WMI. These last records name no source, so each is joined to share access or a network logon on the same computer within two minutes, and, when it names an account, only to one by that account; the reasons say how it was joined. A service or remote shell with nothing near it is named in the notes. Tasks and programs started by WMI or DCOM are made on a computer by itself all the time, so only those under a person's account are read (not the computer's own or SYSTEM's), and one with no network logon by that account near it is listed in the notes as taken to be local. Network logons (4624 type 3) support a connection but are not shown alone: a domain controller has thousands. SYSVOL, NETLOGON, other pipes on IPC$, and computer accounts are left out for the same reason.

DCOM. On the computer connecting: PowerShell's GetTypeFromProgID or GetTypeFromCLSID with a computer name, and Security 4648 to RPCSS/…. On the computer connected to: MMC, mshta or an Office program started as a DCOM object (-Embedding, /automation) under a person's account, and the programs those start (Sysmon 1 gives the parent's command line; from Security 4688 only MMC's children are read); network connections accepted by those programs or by explorer.exe, which is how ShellWindows and ShellBrowserWindow show (Sysmon 3); and a remote launch DCOM refused (System 10016, which names the caller's account and address). Without Sysmon, ShellWindows and ShellBrowserWindow cannot be told from Explorer's own work and are not read.

Sysmon's network connections (event 3) give Remote Desktop (port 3389) and WinRM (5985, 5986) at either end, with the other computer's address. Connections to file sharing (445, 139) and the RPC endpoint mapper (135) support a connection, like a network logon, but are not shown alone. Older Sysmon put this computer under "Source" for a connection it accepted, newer puts the other computer there; which end is which is worked out from the host names Sysmon gives, who started the connection, and which end has the server's port.

From the user's own files on the computer connecting. A jump list entry for a file on \\computer\share is a file opened there, at the time the jump list gives, and pairs with that share's access like a command would. The user's NTUSER.DAT names computers the account connected to by Remote Desktop (Terminal Server Client\Servers and its recent list) and shares it used (MountPoints2), but the only time it has is when each key was last written, which is not when a connection was made. So these never pair by time: each is added to the reasons of the connections between the same two computers (for a program started remotely, only when it used that share), and where there is none it is shown as a connection of its own, marked no time and drawn dotted in the lanes. A key written long before the rest is drawn at the lanes' edge, so it does not squash them.

Add each host's Security, System, Terminal Services and WinRM logs (and Sysmon's, if it ran), and its users' NTUSER.DAT and jump lists, under that host. Not read yet: the WMI-Activity log, and shortcut files (their times are the target file's, not when it was opened).

How the ends are paired. Each host's events within two minutes of each other are one end of a connection. The two ends pair when each names the other (the client named one of the other host's names or addresses, and the logon came from one of the first host's) and they are within ten minutes of each other once each host's clock difference from the Details tab is taken off. They pair strongly when within a minute and with the same account at both ends; otherwise possibly, and the reasons say why (further apart, or different accounts: other credentials can be typed at the logon prompt). A connection seen at one end only is listed too, with what that may mean: the other computer is not in the case, its logs are missing, the connection failed, or another program was used. A file share or remote program is often seen at the target only, because few computers log the commands they run.

Names and addresses. Matching depends on what you state for each host on the Details tab: Other names (its full name in the domain, a former name) and IP addresses. When a logon record gives both a workstation's name and the address it came from, that address is taken as that host's, and the notes say so; an address seen for two hosts is not used. Clock differences are written as, for example, 3 minutes ahead, 90 seconds behind or -1m30s.

The views. Graph draws each host as a large circle and each other computer or address as a small one, with an arrow for each direction and kind of connection, labelled with the kind and how many times; drag a circle to move it, click one to list only its connections, click an arrow for those between two. Lanes gives each computer a lane, with time across, and draws each connection as an arrow from lane to lane: the view for following a path from host to host. A filled dot marks an end found in the evidence, a hollow one an end that was not. A bar along the lane of the computer connected to is a Remote Desktop session, from its start until it was logged off, or disconnected when no logoff was found; the list gives its length ("session 39 min") and the reasons say which records ended it. A session's end is found by the logon id the logon gave (Security 4634, 4647 and 4779 carry it) or by the session number and account (LocalSessionManager 23 and 24); a disconnection with no logoff after it may be a session left open or taken up again later. To look at a period, type its start and end (UTC) in the boxes beside the kinds, as 2026-11-20 09:00, or 09:00 for the day of the first connection (a date alone as the end means the end of that day), and press Enter; or drag across the lanes. Both views and the list then show only the connections in it, and a session that began earlier and runs into it; the lanes span just that period, and such a session is drawn as its bar from the edge. Connections with no time are left out of a period, and the summary says how many. Whole time shows everything again. Clicking a host of the case on the graph also opens it into small nodes around it: the accounts its connections name (signed in to it, or connecting out from it), and the USB storage devices its SYSTEM hive records (Enum\USBSTOR: when each was first installed, first and last connected and last removed, by the host's clock corrected). The list repeats them, with the times, a device's serial, and a link to the records; a small node opens its records on the timeline. A USB storage device whose serial is in the SYSTEM hives of two hosts is itself a link between them (the kind USB devices), drawn from the host that had it first to the next, at the time it first arrived there; its reasons give its times on each and say whether they overlap (it went back and forth). A serial shows the same device, not who carried it or what was copied. A serial Windows made up for a device with none (its second character is &) belongs to one computer and is never matched. Each connection lists its reasons, opens each end's events (with the time as that host's clock had it), and opens all of them on the timeline. The other way round, an event on the timeline that is read for this tab says so in its panel ("Read for the Connections tab: …") with Show its connections, which opens the tab on the connections it is part of, the rest dimmed; Show all brings back the others. An event can be read and still be part of none: a network logon alone, or a service or task taken as local (the notes say which). A connection 127.0.0.1 → host is a session from the computer itself, which is how a tunnel (a port forwarded over SSH, a proxy) shows.

Like the analysis checks, this adds nothing to the case and is recorded in the audit log when run. A pair is consistent with one connection; it does not prove it.

Case and host details

A report needs facts no artefact holds: the case reference, who asked for the examination, and for each computer its make, model, serial number, who collected it and how, and what its clock read against a reference when it was seized. Enter them on the Details tab. Where Atropos found a value in the evidence (the host name, the time zone, the Windows version) it is shown beside the field for comparison. Changes are kept as a history; an earlier value is never overwritten.

Hosts. A form appears for each computer the evidence names: Atropos reads a computer's name and time zone from its SYSTEM registry hive (Windows\System32\config\SYSTEM), and has each name it finds ready with its own form. The hive also gives the computer's name in its domain and the address each network interface last had, set by hand or leased by DHCP; the Connections tab matches other hosts' records on these where no address is stated, and its notes say which were used. An address a hive records is the last one the computer had, not necessarily the one it had at the time, so state the addresses of the period examined when you know them. You can describe a host whether or not the evidence names it: with no SYSTEM hive in the case, a blank host form is shown that starts with the computer's name, and Add host adds more.

Reports and exports

Case report (top right) first verifies the case, then writes one document: what was examined, with hashes; how each item was read and by which version; the details you entered; your groups and notes; and the result of the verification. HTML is for reading and printing, JSON for other tools.

Export (beside the search box) writes the events that match the current search, zoom and group:

CSVFor a spreadsheet. Values that a spreadsheet would treat as a formula are made safe.
JSON linesOne event to a line with every field. The fullest form.
Timesketch JSONLReady to upload to Timesketch.
BodyfileFile times only, for mactime and tools that read its format.

Every export and report is recorded in the audit log with what was asked for.

Integrity and the audit log

Nothing in a case is ever changed or deleted. Evidence is stored once under its hash. Events belong to the parse run that made them, and each run is sealed with a digest of its events. Corrections are new entries. The Audit log tab lists everything that has happened, each entry carrying the hash of the one before, so that an entry cannot be altered or removed from the middle without it showing.

Verify integrity re-hashes every stored file, recomputes every run's digest from the events as they are now, compares the runs with what the audit log recorded when each was sealed, and walks the audit chain. It ends with the hash of the newest audit entry. Write that down somewhere outside the case: it is what later proves that nothing was removed from the end of the log.

Time zones

Everything on the timeline is UTC. Many artefacts store UTC already. Others store the computer's local time with no zone, and those have to be converted. The TZ dot on each row says how:

native-utcThe format stores UTC. Nothing to decide.
explicit-offsetThe value carried its own offset.
host-registryLocal time, converted with the zone read from the computer's own SYSTEM hive in the same submission. This is why the hive should be added with the rest.
examiner-setLocal time, converted with a zone you stated when starting Atropos (--local-zone Europe/London). Your statement is in the audit log.
assumedNo zone could be established, so the time was taken as UTC. It may be wrong by the computer's offset. These rows are orange; tz:assumed finds them all.

A local time that falls in the hour repeated or skipped when the clocks change cannot be converted with certainty. Such an event carries a caveat, shown when you open it.

Command line

Everything the page does to a case can also be done without it. One Atropos process works on a case at a time.

atropos serve --case DIRThis interface. It listens only on this computer.
atropos ingest --case DIR PATH…Add files or folders. On Windows this keeps alternate data streams, which the page cannot. --host NAME says which computer they come from (added to the hosts if new); --not-from-host TEXT says they come from none, and where from.
atropos verify --case DIRThe integrity check.
atropos export --case DIR --format csv --query "…" -o FILEExport a search. Formats: csv, jsonl, timesketch, bodyfile. --group NAME for one group.
atropos report --case DIR --format html -o FILEThe case report.
atropos analyse --case DIRThe checks and the connections between hosts. --check anomalies, timestamps or connections for one; --tag to tag what the anomaly checks find.

Useful with any of them: --examiner NAME (recorded in the audit log; your login name otherwise) and --local-zone ZONE. Run atropos with no arguments for the full list.

Limits worth knowing

  • A finding, a tag, or an event is evidence of what the artefact recorded, and no more. "File modified (ShimCache)" is the file's modification time as Windows cached it, not the time it ran.
  • A browser database copied from a running browser keeps its newest entries in a separate -wal file beside it. Add that file too: Atropos works out from its contents which database it belongs to, applies it to a working copy (never to the evidence) and reads that, and the database's notes say how many transactions were applied. Add it later and the database is read again by itself. A database in that mode with no log that fits says so in its notes.
  • A Chromium browser's Sessions folder holds the tabs that were open and those recently closed, with each tab's back-and-forward history and when it was closed. Private windows' tabs are not saved there. The newest browsers can encrypt these files; Atropos says so when it meets one.
  • The Windows Search index records files as the indexer last saw them, including files that have since been deleted or moved; its file times are copies, taken when the item was indexed. Search source:windows-search.
  • OneDrive's databases record files as the sync client knew them. A "downloaded" event means an online-only file was fetched because something opened it. SafeDelete's deletions name the program that deleted the file, at the time OneDrive noticed. OneDrive's own logs (.odl) hide file names by encrypting them: add the general.keystore from the same folder and they are decrypted, even if you add it later. Search source:onedrive.
  • Synced browser history is marked as such: a visit made on another device signed in to the same account is not evidence that this computer was used.
  • Cookie values and saved passwords are never read. Atropos records that a cookie or a saved login exists, for which site, and when.
  • Records found by searching (WMI subscriptions, entries in unused directory space) may be old or deleted versions. Their notes say how they were found.
  • A deleted registry key is shown at the time it was last written, which is before it was deleted, not the moment of deletion. When its parent key is also gone, its path starts with …\. Search type:"registry-key-deleted (last written)" to see them all.
  • FAT stores times on the clock of whatever wrote them, without saying which time zone that was, and to two seconds; the last-access time is only a day. Atropos converts them using the computer's zone from its registry if one is in the case, or UTC otherwise, and the event says which. A stick written by a camera or another computer may have used another zone. exFAT usually records the zone, and those times are exact.
  • Memory images are out of scope. Use Volatility, and add what it produces as a log if you want it on the timeline.
  • Not opened yet: LVM, XFS, Btrfs and Mac file systems, the ext journal, VMDK disks made of several files, and deleted folders on FAT (their own entries are shown, not what was in them). The README lists what each reader covers and docs/COMPARISON.md how its output compares with other tools.
  • The timeline loads rows as you scroll. In a case of millions of events, zoom in on the chart to move around; do not try to scroll the whole of it.
